# Архитектура

## Назначение

Онлайн-деканат проверяет, что в документе присутствуют сведения, необходимые по подключённому Положению, и отвечает только на вопросы, для которых есть основание в документе или правилах. Сервис не принимает документ и не подтверждает его подлинность.

## Компоненты

| Компонент | Файлы | Ответственность |
| --- | --- | --- |
| HTTP-слой | `app/main.py` | FastAPI-маршруты, лимиты, сессии, заголовки безопасности и экспорт. |
| OCR | `app/ocr.py` | Открытие PNG/JPEG/PDF, коррекция изображения, Tesseract, координаты слов и оценка качества. |
| Извлечение | `app/extraction.py` | Классификация типа, поиск меток, нормализация дат и периодов, доказательства полей. |
| Профиль кейса | `app/official.py` | Контракт рабочего профиля, визуальные отметки, комплектность и структурированные ответы. |
| Правила | `app/knowledge.py`, `app/reasoning.py` | Импорт Положения, поиск по пунктам, ответы для пользовательских правил. |
| Досье | `app/dossier.py`, `app/main.py` | Проверка согласованности реквизитов и периодов между уже проанализированными документами. |
| Визуальные отметки | `app/vision.py` | Консервативные признаки подписи и печати. |
| Экспорт | `app/report.py`, `app/bundle.py` | HTML-протокол, JSON, обработанные страницы и манифест SHA-256. |
| Защита демонстрационных данных | `app/redaction.py` | Создание JSON-копии без содержимого документа и прямых идентификаторов. |
| Маршрутизация | `app/workflow.py` | Консервативное определение следующего действия сотрудника по статусам проверок. |
| Очередь и решение сотрудника | `app/main.py`, `web/app.js` | Минимальные карточки активных сессий, фильтрация по следующему действию, фиксация маршрута с основанием и переход к доказательной карточке. |
| Интерфейс | `web/` | Локальный SPA без внешних зависимостей. |

## Поток обработки

1. Клиент отправляет файл, вопрос, выбранный тип или `auto` и идентификатор активной базы правил.
2. `main.py` проверяет размер, расширение, число страниц и доступность OCR; работа выполняется в ограниченном пуле из двух задач.
3. `ocr.py` открывает файл. PDF растеризуется через `pypdfium2`, изображения корректируются OpenCV: ориентация, наклон, контраст и освещение.
4. Tesseract возвращает строки, слова, confidence и координаты. Для номера документа при необходимости выполняется локальное повторное чтение участка.
5. `extraction.py` определяет тип по заголовкам и маркерам. Затем извлекает поля схемы: значение, статус, confidence и список координат-источников.
6. Для профиля «Меридиан» `official.py` нормализует даты в ISO 8601, подтверждает только визуально найденные подписи/печати и вычисляет комплектность по пунктам Положения.
7. Ответ формируется из разрешённых сценариев: поле документа, комплектность, требование Положения, окончательное решение сотрудника или отказ при отсутствии основания.
8. В памяти создаётся сессия. Браузер получает результат, изображение обработанной страницы, подсветку источника и возможные действия пользователя.
9. По запросу сотрудника `dossier.py` связывает до восьми сессий, сравнивает нормализованные ФИО, группу и направление, проверяет пересечение периодов отпуска и практики и возвращает источники каждого вывода.
10. Кабинет сотрудника получает `/api/queue`: в ответ попадают только статус, тип, количество готовых полей, время, число ручных исправлений и тип уже записанного решения. При открытии элемента клиент запрашивает `/api/session/{id}` и показывает существующую карточку проверки.
11. Сотрудник фиксирует `POST /api/decision/{id}` с причиной: возвращает документ на доработку либо, после устранения замечаний, направляет его на дальнейшее рассмотрение. Решение сохраняется в сессии, истории решений и экспортах; это маршрут обработки, не автоматическое принятие документа.

## Профили правил

Стандартный профиль определяется полем `profile: "meridian-v1"` в `config/official-rules.json`. Только он использует фиксированные схемы `official-documents.json` и структурированный формат результата участника.

Импортированное Положение никогда не переключает сервис на этот профиль только из-за `demo=false`. Оно остаётся в настраиваемом режиме с собственной базой пунктов. Это разделение покрыто регрессионным тестом.

## Состояние и жизненный цикл

Сессии документов, загруженные правила и досье хранятся только в памяти процесса. Время жизни — 30 минут неактивности. Одновременно хранятся не более 12 сессий документов, 8 баз правил и 8 досье. При остановке процесса память очищается.

Выбор сделан намеренно для локального сценария: данные не попадают в базу данных и не требуют учётной записи. Для общего серверного развёртывания потребуются отдельные хранение, авторизация, аудит доступа и политика удаления данных.

## Формат доказательств

У каждого поля есть `value`, `status`, `source`, `confidence` и `evidence`. `evidence` содержит страницу, прямоугольник и текст OCR. Клиент использует эти координаты для подсветки фрагмента.

`Пакет проверки` содержит:

- `analysis.json` — полный результат, снимок правил и ручные исправления;
- `report.html` — печатный протокол;
- `pages/` — обработанные страницы, к которым относятся координаты;
- `MANIFEST.json` — SHA-256 вложений;
- `README.txt` — состав пакета и ограничения.

Исходный файл не включается в пакет. Хеши контролируют целостность пакета, но не заменяют электронную подпись.

`GET /api/export/{id}/redacted` создаёт отдельную обезличенную JSON-копию. В неё не попадают изображение, OCR-текст, координаты источников и хеш исходного файла; ФИО и номер документа маскируются. Обычный экспорт и пакет доказательств не изменяются.

## Границы точности

Извлечение рассчитано на печатные документы, близкие к схемам рабочего профиля. Низкое разрешение, сильные тени, рукописный текст и непривычная вёрстка могут требовать ручного исправления. Визуальный модуль сообщает о признаках подписи или печати; он не устанавливает их подлинность.
