# Реестр продуктовых возможностей

Этот документ фиксирует отличия сервиса, их назначение и состояние. Он используется как источник для демонстрации, технического обсуждения и дальнейшей доработки.

## Реализовано

| Возможность | Польза | Где проверить |
| --- | --- | --- |
| Проверяемый ответ | Ответ содержит ссылку на пункт Положения или кнопку перехода к полю на изображении. | Карточка ответа и карточка документа. |
| Карта источников | У каждого извлечённого поля есть страница и координаты; клик по значению подсвечивает фрагмент. | Результат анализа → «Карточка документа». |
| Паспорт качества страницы | До работы с полями сервис сообщает, достаточно ли качества снимка и почему требуется внимание. | Результат анализа → «Источник». |
| Версия правил в результате | Каждая сессия хранит копию Положения, его версию и SHA-256. | Раскрыть «Проверки правил и история исправлений» или выгрузить JSON. |
| Ручная верификация | Пользователь исправляет поле или подтверждает визуальную отметку; действие остаётся в журнале. | Карандаш рядом с полем. |

| Консервативный отказ | Если в документе и Положении нет основания, сервис не создаёт предположение. | Сценарий «Проверка границ ответа». |

| Обезличенная выгрузка | Результат можно безопасно передать на демонстрацию, в службу качества или команде разработки без исходного документа и прямых идентификаторов. | Кнопка «Обезличенная копия» и API `/api/export/{id}/redacted`. |
| Маршрут обработки | Результат проверки превращается в следующий рабочий шаг: запросить дополнение, провести ручную сверку или передать документ на итоговое решение сотруднику. | Карточка «Маршрут обработки» в результате. |
| Кабинет сотрудника и очередь | Сотрудник видит активные документы, сгруппированные по следующему действию, и открывает доказательную карточку прямо из очереди. Список не содержит изображений, OCR-текста или значений полей. | Раздел «Кабинет сотрудника» и API `/api/queue`. |
| Разделённые рабочие сценарии | При первом входе посетитель выбирает путь студента или сотрудника. Студент видит только подачу и личный результат, сотрудник — очередь, досье, правила и карточки документов из очереди. | Стартовое окно «С чего начнём?» и разная навигация после выбора. |
| Статус обращения для студента | Решение сотрудника преобразуется в понятный следующий шаг: доработать документ или ожидать дальнейшего рассмотрения. Студент видит основание и время обновления в своей карточке. | Карточка «Статус обращения» под результатом проверки. |
| Ход обращения | Студент видит последовательность существенных событий: запуск проверки, ручные уточнения реквизитов и решения сотрудника. Это делает процесс прозрачным без раскрытия чужих документов. | Карточка «Ход обращения» под статусом. |
| Новый тип через конфиг | Новая схема документа и правила добавляются без изменения Python-кода; перед запуском профиль проходит структурную проверку. | `examples/student-pass-profile/` и `python -m scripts.validate_profile`. |
| Предконтроль снимка | До отправки изображения браузер локально оценивает разрешение, яркость, контраст и резкость и предлагает переснять проблемный кадр. | Блок под выбранным файлом в сценарии студента. |
| Памятка по подготовке документа | Помогает студенту заранее выбрать корректный формат, сделать читаемый снимок и понять, какую проверку запустить. Это уменьшает число повторных подач без регистрации и лишних действий. | Раздел «Как подготовить документ» в навигации студента. |
| Проверка комплектности одним действием | Студент может запустить стандартную проверку обязательных сведений, не формулируя вопрос вручную. | Кнопка «Проверить только комплектность». |
| Конструктор обращения | После предварительно успешной проверки студент получает редактируемый черновик обращения в деканат с темой и приложением. При замечаниях сервис вместо ложной готовности формирует понятную памятку по доработке. | Карточка «Следующий шаг» в результате и API `/api/appeal/{id}`. |
| Паспорт результата | Итог проверки переводится в понятный статус: готовность, число пройденных требований, конкретные замечания и безопасный следующий шаг. Каждое замечание ведёт к соответствующему полю на снимке. | Верхняя карточка «Паспорт результата» после анализа. |
| Контроль структуры документа | Сервис объясняет, распознана ли ожидаемая структура по заголовку и найденным реквизитам, и предупреждает о нестандартном бланке или несоответствии выбранного типа. Это не проверка подлинности. | Строка в «Паспорте результата». |
| Повторная подача с разницей версий | После исправления студент загружает новую версию и видит, какие поля исправлены, ухудшились или изменились. | Кнопка «Загрузить исправленную версию» в результате. |

## Досье студента

### Пользовательский сценарий

1. Сотрудник добавляет в досье справку об обучении, заявление и документ о практике после их самостоятельной проверки.
2. Каждый файл проходит текущую проверку без изменения логики распознавания.
3. Сервис строит сводку: ФИО, группа, направление, даты и статусы документов.
4. Если поле расходится между документами, сотрудник видит оба источника и фиксирует решение с основанием.
5. Итоговая сводка выгружается в JSON для передачи в следующий этап процесса или для хранения с протоколами отдельных документов.

### Проверки между документами

| Проверка | Пример результата |
| --- | --- |
| Совпадение ФИО | «ФИО совпадает в 2 из 2 документов» или «Нужно сверить: в заявлении и справке разные значения». |
| Согласованность группы и направления | «Данные совпадают» либо ссылки на оба поля-источника. |
| Периоды и даты | «Период практики не пересекается с академическим отпуском» или объяснение пересечения. |
| Готовность добавленных документов | Статус анализа показывает, есть ли обязательные сведения в каждом файле. |
| История решения | Система сохраняет дату и комментарий к подтверждённому расхождению в пределах жизненного цикла досье. |

### Технический состав

- сущность `dossier` хранит ссылки на существующие сессии документов, не дублируя OCR-данные;
- `app/dossier.py` нормализует ФИО, группу и направление, а также проверяет пересечение периода академического отпуска с периодом практики;
- `POST /api/dossiers`, `GET /api/dossiers/{id}`, `POST /api/dossiers/{id}/resolve` и `GET /api/dossiers/{id}/export` отдают объяснимую сводку и её JSON-выгрузку;
- интерфейс показывает состав досье, статус каждого документа, источники расхождения и комментарий сотрудника;
- проверки покрыты фикстурами с конфликтом ФИО и пересечением периодов.

### Ограничения текущей версии

Досье существует только в памяти локального процесса и доступно 30 минут после последнего обращения. Оно может содержать до восьми документов, которые ещё не были удалены из текущей рабочей сессии. Сервис отмечает расхождения и пересечения, но не принимает юридическое решение и не определяет подлинность документов.

## Обезличенная выгрузка

### Зачем она нужна

В вузе результат проверки нередко обсуждают вне рабочей смены: на демонстрации, в команде качества, с технической поддержкой или на защите проекта. Обычный экспорт содержит данные конкретного студента. Обезличенная копия оставляет полезные для разбора статусы, правила, качество страницы и результат проверки, но исключает содержимое документа.

### Что делает сервис

- заменяет имя файла нейтральным названием;
- удаляет изображения страниц, исходный OCR-текст, координаты и хеш исходного файла;
- маскирует ФИО студента и руководителя, а также номер документа;
- маскирует эти значения и в журнале ручных исправлений;
- оставляет тип документа, статус, пункты правил, качество страницы и неперсональные поля, необходимые для объяснения результата.

### Польза и границы

Функция снижает риск случайной передачи персональных данных при показе продукта. Она не является юридической процедурой обезличивания и не заменяет регламент вуза: перед внешней передачей данных требуется применить правила организации и проверить сформированный файл.

## Маршрут обработки

### Зачем он нужен

Сотруднику недостаточно увидеть распознанный текст и перечень полей: нужно быстро понять, что делать с конкретным документом. Маршрут обработки связывает технические результаты проверки с последовательностью действий деканата, не подменяя решение сотрудника.

### Логика

| Статус | Когда появляется | Практическое действие |
| --- | --- | --- |
| «Запросить дополнение» | Не найдены обязательные сведения или обнаружена ошибка в данных. | Запросить корректную версию документа и повторить проверку. |
| «Провести ручную сверку» | Часть полей или визуальных отметок требует подтверждения. | Сверить отмеченное поле с оригиналом и подтвердить либо исправить его. |
| «Передать на итоговое решение» | Обязательные проверки прошли. | Передать сотруднику; сервис не принимает документ автоматически. |
| «Определите тип документа» | Схема документа не определена. | Выбрать тип вручную и повторить проверку. |

В каждом статусе сервис выводит причины и следующие действия. Маршрут строится только по результатам проверки и подключённому Положению; сроки рассмотрения и правовые последствия он не выдумывает.

## Кабинет сотрудника

### Что делает

После проверки документ остаётся в короткоживущей рабочей очереди. Кабинет показывает только безопасную операционную сводку: тип документа, число подтверждённых полей, статус следующего шага, время запуска и число ручных исправлений. Доступны фильтры «Дополнение», «Сверка» и «К решению».

Открытие строки получает исходную сессию и возвращает сотрудника к полной карточке: изображению, подсветке источников, пунктам Положения, журналу правок и экспорту доказательств. После ручного исправления маршрут пересчитывается теми же правилами, что и при первоначальном анализе.

### Зачем это нужно

Студенту не нужно разбираться в служебной очереди: он получает понятный ответ по своему документу. Сотрудник, наоборот, начинает с приоритета работы, а не с набора файлов. Это делает демонстрацию похожей на реальный процесс деканата и показывает, где остаётся обязательная ручная ответственность.

### Технические границы

`GET /api/queue` возвращает минимальные карточки без OCR-текста, изображений и извлечённых значений. `GET /api/session/{id}` открывает карточку только в текущем локальном демонстрационном контуре. Очередь существует в памяти до 30 минут и не является системой разграничения доступа; для промышленного запуска нужны серверная аутентификация, роли, аудит и защищённое хранилище.

## Выбор рабочего сценария

Стартовое окно разделяет две роли уже в первом экране: студент попадает к загрузке и понятной проверке документа, сотрудник — в очередь и рабочие инструменты. После выбора меняется не только стартовая страница: студенту доступны «Мои документы» и сведения о сервисе, а сотруднику — кабинет, досье, основания проверки и карточки документов из очереди. Выбор сохраняется только в пределах вкладки браузера и доступен для смены из шапки. Это сознательно обозначенный демонстрационный механизм навигации, а не авторизация: реальные права доступа должны проверяться сервером после интеграции с учётной системой вуза.

## Решение сотрудника

В открытой сотрудником карточке доступна отдельная форма решения с обязательным основанием. Она поддерживает два маршрута: «Вернуть на доработку» доступен на любом этапе, а «Направить на дальнейшее рассмотрение» — только когда проверка не содержит нерешённых замечаний. Действие, время и текст основания записываются в результат, историю решений, JSON-выгрузку и пакет проверки. Сервис намеренно не использует формулировки «одобрить» или «принять документ»: проверка комплектности не подтверждает подлинность и не заменяет решение уполномоченного сотрудника.

В списке очереди показывается только факт и тип решения без свободного текста. Полное основание видно после открытия уже существующей карточки. В текущей демонстрации решение существует в памяти 30 минут и не привязано к личности сотрудника; для промышленного применения нужны авторизация, неизменяемый журнал и разграничение прав.

## Принципы отбора новых функций

1. Новая функция должна усиливать проверяемость решения, качество входных данных или работу сотрудника.
2. Каждый вывод должен иметь источник, версию правил или понятный статус ручной проверки.
3. Локальная обработка и отсутствие постоянного хранения сохраняются, пока не появится отдельная модель доступа и хранения.
4. Перед включением в основной сценарий функция получает тест и краткое описание в этом реестре.
